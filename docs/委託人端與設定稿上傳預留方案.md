# 委託人端與設定稿上傳預留方案

## 目前保留的資料結構

每張委託單已保留 `clientPortal` 物件，包括 `enabled`、`accessTokenHash`、`expiresAt` 與 `referenceFiles`。在未啟用委託人功能前，這些欄位不會對外暴露，也不會建立公開讀取規則。未來可據此建立兩個不同頁面：一個由委託人填寫初步需求與上傳設定稿，另一個僅供查看已核准的案件狀態。

| 頁面 | 委託人可做的事 | 不可取得的資料 |
| --- | --- | --- |
| 初步填單頁 | 填寫聯絡方式、需求、期限、上傳設定稿，送出待確認案件。 | 排單全貌、其他案件、內部報價、付款紀錄。 |
| 限時進度頁 | 以短效連結查看案件名稱、目前進度、下一步與公開期限。 | 聯絡資料、設定稿原檔、價格、訂金／尾款、內部備註。 |

## 為何不能讓 GitHub Pages 直接上傳

GitHub Pages 是純靜態前端，任何放進前端的服務金鑰、長效上傳 Token 或 R2 API 憑證都可被使用者瀏覽器取得。因此，設定稿上傳必須由一個**小型受保護的伺服器端端點**先核發一次性短效上傳權限；前端只拿到指定檔案路徑、指定格式與短有效期的 URL。

> Cloudflare R2 的預簽名 URL 可暫時授權單一物件的 PUT、GET 或 DELETE 操作，但 URL 本身是持有人憑證，應縮短有效期並限制 Content-Type 與 CORS。[1]

## 建議架構：GitHub Pages + Cloudflare Worker + 私有 R2

此方案可維持繪月錄主網站由 GitHub Pages 發布，僅把「核發上傳 URL」與「驗證限時碼」交由 Cloudflare Worker 執行。R2 API Secret 僅存於 Worker 的 secret，不會出現在 GitHub Pages 或委託人的瀏覽器中。

```text
委託人填單頁
    │  短效填單權杖 + 檔案中繼資料
    ▼
Cloudflare Worker（驗證權杖、檔案大小與格式）
    │  單次 PUT 預簽名 URL，10 分鐘失效
    ▼
私有 Cloudflare R2：artist/{commissionId}/references/{fileId}
    │
    └── Worker 僅把檔名、MIME、大小、儲存鍵寫入 Firestore
```

Worker 應接受 PNG、JPG、WEBP、PDF 等有限類型，並在上傳前限制單檔大小與檔案數量。查看設定稿時，Worker 另核發短效 GET URL；不可把 R2 bucket 直接設為公開。R2 官方文件說明預簽名 URL 可限制單次操作與有效時間，且瀏覽器上傳需配置 CORS。[1]

## Supabase 是否可用

Supabase Storage 可以保存圖片、文件與一般檔案，並以 Row Level Security 控制存取，因此**技術上可以接受設定稿**。[2] 不過委託人不登入時，仍需要 Edge Function 或其他受保護端點驗證填單權杖、限制路徑及簽發上傳權限。若直接把具有寫入能力的 service role key 放入 GitHub Pages，會破壞所有存取控制。

| 方案 | 對靜態 GitHub Pages 的要求 | 建議用途 |
| --- | --- | --- |
| Cloudflare Worker + 私有 R2 | 需建立 Worker 與 R2；Worker 保管簽名用憑證。 | **未來設定稿上傳的優先方案**。 |
| Supabase Storage + Edge Function | 需建立 Supabase 專案、RLS 與 Edge Function。 | 若後續也想用 Supabase Database／Auth 時可選。 |
| Firebase Storage | 需啟用 Cloud Storage 與可能的計費設定。 | 目前已依需求移除，不建議重新加入。 |

## 啟用前的必要安全檢核

啟用委託人端前，應新增以下能力：短效 Token 的雜湊保存與撤銷、每個 Token 的檔案數與大小上限、檔案 MIME／副檔名雙重驗證、上傳完成的 metadata 確認、到期後不可讀取的預簽名 URL，以及管理者刪除檔案的流程。公開進度頁也應只回傳白名單欄位，不能直接讓客戶端讀取 Firestore 完整委託單。
