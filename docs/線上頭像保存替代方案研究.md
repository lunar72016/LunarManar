# 線上頭像保存替代方案研究

研究日期：2026-08-18

## 選項摘要

| 服務 | 免費方案概況 | 靜態 GitHub Pages 上傳方式 | 安全性與適合度 |
| --- | --- | --- | --- |
| Supabase Storage | 免費方案含 1 GB 檔案儲存與 5 GB 快取流量；閒置一週的免費專案可能暫停。 | 使用公開 anon key 與 Storage API，但需在 Supabase 建立帳號、bucket、RLS 規則，並另外處理登入／授權。 | **較安全但設定較多**。Storage 預設拒絕上傳，RLS 可依 bucket、資料夾與 authenticated user 限制操作。適合未來要擴大檔案功能時採用。 |
| Cloudinary | 官方文件支援在瀏覽器端以 unsigned upload preset 直接上傳。 | 前端需暴露 cloud name 與 unsigned preset 名稱。 | **不建議作為本專案的預設方案**。Preset 名稱可被前端取得；雖可限制檔案格式、大小與 public ID，但在無後端簽章／proxy 的 GitHub Pages 環境，無法可靠保證只有繪師帳號可上傳。 |
| ImageKit | 提供 Forever Free 方案與整合式媒體儲存。 | 官方用戶端上傳流程通常需簽章；安全簽章應由後端產生。 | **不適合純靜態前端直接整合**。若沒有安全後端，不能把私密 API 金鑰或簽章邏輯放在 GitHub Pages。 |
| 瀏覽器本機儲存 | 無外部費用。 | 將裁切後的小型頭像以 IndexedDB／localStorage 保存。 | **最適合目前單人用途且零成本**。缺點是更換裝置或清除瀏覽器資料後需重新上傳；委託資料仍可繼續用 Firestore 跨裝置同步。 |

## 結論

在「純 GitHub Pages、單人繪師、避免付款、沒有可信後端」的前提下，本機頭像是安全且維護成本最低的方案。若未來確實需要跨裝置同步頭像，Supabase Storage 是較可控的免費候選方案，但需要額外設定 Supabase Auth／RLS 或可信後端來確保只有本人能寫入；不宜把 service role key 放進前端。
